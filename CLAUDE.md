# CLAUDE.md

Project rules for Claude Code when working in this repo. Keep this file current: when a new convention gets established or an old one changes, update this file in the same session, not later.

## Project

Specialty EHR — PHP backend (custom router, no framework) + vanilla JS SPA frontend, running under WAMP. Current focus branch: Cardiology-specialty EHR.

- Backend entry: `public/index.php` → `backend/routes/api.php` → `backend/app/Controllers/*.php`
- DB: MySQL `ehr_db` via `backend/app/Models/Database.php` (PDO, `PDO::ATTR_EMULATE_PREPARES => false`, native fetch mode)
- Frontend: single large `public/js/app.js`, hash-based router (`public/js/router.js`) — only one module's DOM exists in `#app-root` at a time, so `.athena-*` style classes can be reused across modules safely, but element IDs should still stay unique per module
- Popups: **every** popup in the app is now a real Bootstrap 5 modal (vendored locally: `public/css/bootstrap.min.css`, `public/js/bootstrap.bundle.min.js`). SweetAlert2 and the older custom `public/js/components/modal.js` (`Modal` class) were both fully removed — neither file exists anymore, and there is no other popup mechanism to reach for. Two patterns cover everything:
  - **Dynamically-built popups** (alerts/confirms/prompts/forms assembled from JS strings, formerly `Swal.fire`) go through `BsAlert` (`public/js/components/bootstrap-alert.js`) — same method surface as SweetAlert2 (`fire`, `close`, `showValidationMessage`, `showLoading`, `getPopup`, `getCancelButton`, `getConfirmButton`, `clickConfirm`, `DismissReason`), backed by a singleton reused `bootstrap.Modal` instance, so existing `preConfirm`/`didOpen`/`.then()` call sites work unchanged.
  - **Static, pre-rendered form modals already in the page HTML** (the clinical encounter workflow, the addendum modal, and the billing/invoice/CPT modals in `clinical_modal.php` / `billing.php`) are wired directly with `bootstrap.Modal.getOrCreateInstance(el, { backdrop: 'static', keyboard: false }).show()/.hide()` at each open/close call site — no shared helper, called inline, matching the existing per-site style. `backdrop:'static', keyboard:false` is intentional: none of these forms had backdrop-click/ESC dismiss before, and they hold real unsaved data, so that non-dismiss behavior is preserved rather than silently adding a new way to lose work.
  - Class names: these modals use plain Bootstrap class names (`.modal`, `.modal-dialog`, `.modal-content`, `.modal-header`, `.modal-body`, `.modal-footer`) — the `legacy-modal-*` prefix that existed for one session (while `modal.js` and Bootstrap briefly coexisted) is gone now that `modal.js` is deleted. Don't reintroduce a `legacy-modal-*`/bare `.modal-*` split — there is only one modal system now.
  - **Bootstrap version note**: when calling `bootstrap.Modal.getOrCreateInstance(el, options)`, the `options` argument is only honored the *first* time an instance is created for that element; later calls silently ignore it and return the cached instance. Pass the same options at every call site for a given modal (all current call sites do).
  - **Modal scrolling — one scroll container only.** `theme.css`'s shared `.modal-dialog`/`.modal-content`/`.modal-body` rules already constrain every modal to the viewport and make `.modal-body` the *only* scrollable region (`.modal-dialog { max-height: calc(100% - var(--bs-modal-margin)*2) }`, `.modal-content { max-height: calc(100vh - var(--bs-modal-margin)*2); overflow: hidden }`, `.modal-body { flex: 1 1 auto; min-height: 0; overflow-y: auto }` — the `max-height:100%` Bootstrap normally uses on `.modal-content` doesn't work here since `.modal-dialog` only has a `max-height`, not an explicit `height`, so percentage resolution fails; it has to be viewport-relative directly). **Never add `max-height`/`overflow-y:auto` to a `BsAlert.fire({ html: ... })` call's own content wrapper `<div>`** — that was a SweetAlert2-era leftover (SweetAlert2's popup body didn't auto-scroll, so call sites self-scrolled their content) found at 13 call sites and removed; nesting a second scrolling container inside `.modal-body` is exactly how the double-scrollbar bug happened. New long-content popups should render plain, unconstrained HTML and let `.modal-body` scroll them.
- **Bootstrap's `.card` is `display:flex; flex-direction:column`.** Since Bootstrap was vendored, any element that carries the class `card` *and* is meant to be a flex **row** must set `flex-direction: row` explicitly - otherwise its children stack and centre (this is exactly what broke the patient wizard header). Same goes for other Bootstrap-defined classes that our older custom CSS silently relied on being unstyled.
- **App toasts need Bootstrap's `show` class.** `Toast.show()` (`components/toast.js`) builds `<div class="toast show toast-{type}">`; Bootstrap's `.toast:not(.show){display:none}` otherwise hides every toast (this silently hid *all* success/error toasts app-wide after Bootstrap was vendored - a failed Save looked like nothing happened). Don't drop `show`. Also: `app.js` imports `./components/toast.js` with no `?v=`, so after editing a component file a normal reload can serve the cached copy - hard-reload (Ctrl+F5) when verifying.
- PII fields (`first_name`, `last_name`, `dob`, `ssn`, `phone`, `address`, etc.) are stored via `EncryptionService::encrypt()` — AES-256-GCM with a **random IV per call**, so identical plaintext never produces identical ciphertext. Never write a `WHERE some_encrypted_col = ?` query. If you need to match on an encrypted field (duplicate detection, lookups), use a deterministic **blind index** column instead (`EncryptionService::blindIndex()`, HMAC-SHA256) — see `patient_match_hash` on `patients` for the reference implementation.
- `backend/config/schema.sql` is a historical snapshot, not the live source of truth — it lags the actual DB. Treat the live DB as authoritative; append new migrations to the end of schema.sql as a dated/commented `ALTER TABLE` block for documentation, but always apply the change to the live DB directly too.
- **`initClinicalHandler()` (`app.js`) is dead code.** It belongs to the `#clinical` route, which is not in the sidebar nav and crashes with pre-existing `TypeError`s if reached directly — it is never invoked in practice. Anything declared *inside* that function (or inside any other route's `init*Handler`) only exists while that route's module is active; a function nested in there is `undefined` everywhere else. This has caused two real bugs: `toggleCardioWorkflow` silently never ran on `#patients`, and the entire specialty-aware `printEncounterReport()` (with full Cardiology/Ortho/Derma/etc. detail) was unreachable from the real "Print Report" button, which used a separate, much simpler generic template instead. **Rule of thumb: anything that must work from more than one route — or from the real `#patients` chart at all — goes at true top-level scope** (declared before the `init*Handler` functions, exposed on `window` if another module/file needs to call it, wired via a delegated `document.addEventListener` if it responds to DOM events), never nested inside a specific route's init function.
- **The real clinical encounter form has no single top-level `<form>`.** `clinical_modal.php` is a set of independent per-section `<form>` elements (`vitals-form`, `history-form`, `cardio-form`, `ortho-form`, …) plus a scatter of standalone hidden inputs; there is no outer form wrapping the whole modal. `window.submitEncounter` (app.js) builds its save payload by reading many individual elements via `getElementById`, not via one form's `FormData` (specialty JSON blobs like `cardio_data` are the exception — each specialty panel's own `<form>` *is* read via `FormData` for just that blob). If you add a new generic (non-specialty) SOAP field, it needs its own real element with a stable ID *somewhere* in this file — `submitEncounter`/`_syncCustomTabsToDOM` silently no-op (not throw) when the element they expect doesn't exist, so a missing field fails silently rather than with a helpful error. This is exactly what happened with `#chief-complaint`/`#hpi`/`#ros`/`#pe-*` (now fixed — see hidden fields near `#clinical-family-history`): they were read/validated/synced by JS for every specialty, but the actual `<input>`s never existed in the PHP, so every real encounter save silently failed with a false "Chief Complaint is required" error until they were added.

## Rules — must follow on every change

1. **Verify SQL placeholder/value counts before testing.** When editing a multi-column `INSERT`/`UPDATE` in a Controller, count columns, `?` placeholders, and bound values independently (a small PHP script with a bracket-depth-aware comma counter, run via Bash) before running the app. Manual eyeballing on large statements has produced silent off-by-one bugs before.
2. **Lint after every edit.** `php -l <file>` for any touched PHP file, `node --check public/js/app.js` for any JS edit. Do this before live verification, not instead of it.
3. **Apply schema changes to the live DB, not just schema.sql.** Write a one-off PHP/PDO script to the scratchpad directory, run it against the live `ehr_db`, confirm the result (e.g. `SHOW COLUMNS`, row counts), then mirror the change into `schema.sql` as a migration block.
4. **Live-verify in the browser before calling a change done**, using the Playwright MCP tools. This SPA needs a full reload cycle to pick up module changes reliably — navigate to a bare URL (`.../public/index.php`) first, then to the target hash route; a same-hash re-navigation can serve stale module state.
5. **Clean up test data created during verification** (delete test patients/records) before ending the task, unless the user asked to keep them.
6. **Preserve existing element IDs when refactoring frontend forms/wizards.** The JS submit/prefill logic is ID-driven; renumbering wrapper structure (steps, sections) is fine, renaming IDs breaks the data pipeline silently.
7. **Use plan mode (EnterPlanMode) before implementing anything that touches 3+ files, changes DB schema, or involves an architectural/design decision** (e.g. warn-vs-block UX choices, new column vs new table). Small single-file fixes don't need it.
8. **Never commit or write local dev credentials into files in this repo**, including this one. Ask the user for current test credentials each session if needed for live verification.
9. **Only commit or push when the user explicitly asks.** Investigation, implementation, and live testing do not imply permission to commit.
10. **Before adding a CSS class to a shared/global stylesheet (`theme.css` especially), grep the target file for that exact class name first.** If it already exists, merge your new properties into the existing rule block — never append a second `.classname { }` for a name already defined in the same file. CSS cascades per-property, not per-block: a later, narrower block doesn't replace an earlier one, it merges with it, and any property the later block doesn't touch silently persists from the earlier block. That's exactly how `.badge-status` ended up with a forced `width: 180px` — a stray second definition, added later in the file, that only overrode 3 properties and left the rest (display, alignment, sizing) merged in from the original.

## Known issues (found, not yet fixed)

A project-wide sweep for duplicate same-file CSS class definitions (the same bug class as `.badge-status`) found genuine partial-merge risk clustered around **Calendar controls**, deliberately left unfixed pending a reported symptom + live verification (no visible bug confirmed yet, and the fix spans two files with layered `!important` rules — higher regression risk than reward without a concrete complaint to verify against):
- `theme.css`: `.nav-arrow-btn` (later block never redeclares the earlier block's fixed 32×32 sizing before adding its own padding — potential icon clipping/off-center), `.btn-today` (earlier block's `!important` padding/font-size permanently wins over the later, presumably-intended values), `.calendar-header-bar` (later block never redeclares `flex-wrap`/`gap` from the earlier one).
- `calendar.css` *also* independently redefines `.btn-today` with its own `!important` padding/font-size, on top of the `theme.css` conflict above — which one actually wins on the live page depends on stylesheet load order and hasn't been empirically checked.

If Calendar's "Today" button or the month-nav arrows ever look visually off, start here.

**Branding / outgoing email:** the user-facing name is **Specialty EHR** everywhere (email sender names and footers, intake and telehealth-join pages, consent wording, invoice print header). The old "CareHealth Family Medicine" / "Primary & Family Care" names were replaced; only the internal Jitsi room prefix `CareHealth_Telehealth_P` remains (an identifier, not display text). Don't reintroduce a hard-coded clinic name - the invoice header reads the active specialty from `#global-specialty-name`.

**Public links (emails to patients/staff):** build them only through `App\Services\AppUrl::publicUrl('page.php?...')` (intake form, telehealth join, new-user login) - never from `HTTP_HOST`/`SCRIPT_NAME` directly. It honours Settings > "Public EHR Base URL" (`system_settings.app_base_url`), whose meaning is *the URL of the project folder that contains `public/`* (e.g. `https://myclinic.com`, `http://192.168.1.20/Specialty_EHR`) - no `/public`. `SettingsController::save` validates/normalizes it via `AppUrl::normalize()` (rejects non-http(s), spaces, query strings; strips a trailing `/public`). Blank = auto-detect from the request, swapping `localhost` for the server's LAN IP, so links then only work on the same network. The old `app_domain` key was dropped (nothing set it). `AppUrl::build()` is the pure, testable half.

**Hard-coded email recipient (found, not changed):** `IntakeController.php` (~line 263) sends the "clinic notice" for submitted intake forms to a hard-coded personal Gmail address. That should be a configurable clinic address (e.g. a `system_settings` key), and it needs an owner decision before changing.

The "Add Diagnoses" patient-chart popup (`app.js`, `preConfirm` around line 8008) is currently broken: its row selector is the literal string `"#modal-diag-tbody .diag - row - item"` (stray spaces around the hyphens), which is an invalid CSS selector and throws `SyntaxError` on submit — no diagnoses can be saved through it until the selector is corrected to `.diag-row-item`. Confirmed pre-existing (unrelated to the Bootstrap-popup migration); not fixed here since it's out of that change's scope.


## Sidebar / navigation conventions (Oct 2026)

- **Menu structure** (`public/modules/sidebar.php`, included by every module page): Dashboard / **Schedule >** (Calendar, Telehealth) / **Patient >** (Patients, Encounters, Diagnoses & Allergies, Medications, Orders & Labs, Referrals, Recalls) / Messages / Billing / Audit & Reports / **Settings >** (System Settings + an "Administration" block: Facility, Specialties, User Management, Roles & Permissions). A new page goes inside the matching group (add its `$activeNav` key to `$navGroups` at the top of the file so the group opens and its parent highlights). Keep the existing element ids (`nav-*`, `nav-parent-administration`, `nav-sub-*`, `sidebar-toggle-btn`, ...) - JS depends on them.
- **Group parents are toggles with no route** (`a.nav-link-parent[data-submenu-toggle]`, ids `nav-parent-schedule|patient|settings`, wrappers `#nav-group-*`). They are opened/closed by the **top-level** `initSidebarGroups()` (one delegated `document` click handler) - never wire a group toggle inside an `init*Handler`; that is exactly what used to make the Administration submenu work only on its own page. Open state = PHP (`$activeNav`) + `localStorage.sidebarOpenGroups`. In the desktop icon-only mode a click on a group icon expands the sidebar first (`setSidebarCollapsed(false)`).
- **"Administration" is a nested dropdown inside the Settings group** (`li.nav-subgroup#nav-parent-administration[data-subgroup]`, toggle `a.nav-subgroup-toggle[data-subgroup-toggle]` = bold label + small chevron right after the text, list `ul.nav-subgroup-list`). It is closed unless the current page is Administration (PHP adds `.subgroup-open`), the same top-level `initSidebarGroups()` handler toggles it, and it is remembered in `localStorage.sidebarOpenGroups` as `sub:administration`. `switchAdminTab()` keeps it open on the Administration page. Another nested dropdown = copy that markup with its own `data-subgroup`.
- **Administration visibility** is still decided in `updateSidebarProfile()` (hides `#nav-parent-administration`, the Administration dropdown inside the Settings group, for non-Super-Admins); the server enforces Super Admin on every Administration endpoint regardless.
- **Styling** lives only in `theme.css` ("Sidebar" and "Sidebar groups" sections) and uses the `--sb-bg/--sb-border/--sb-text/--sb-hover/--sb-active` tokens (defined for light, dark, classic and high-contrast). There is exactly **one** `.sidebar { }` rule - it used to be defined twice; merge into it, don't add another. Active page = blue text/icon, no pill. Submenu rules were moved out of `administration.css`.
- **Responsive:** >= 992px the sidebar is sticky and collapsible to icons (`.sidebar.collapsed`, desktop-only via `@media (min-width: 992px)`); < 992px it is an off-canvas drawer toggled by `body.sidebar-open` (`initSidebarMobile()` creates `#sidebar-mobile-btn` + `#sidebar-backdrop` on `<body>`; closes on backdrop, Esc, page-link click, route change). Only the navigation is responsive - module pages themselves (wide tables, global `table { min-width: 1000px }`) are not.
- Testing the sidebar without credentials: load a module fragment (e.g. `fetch('modules/patients.php')`) into `#app-root` on the login page and dispatch `moduleLoaded` with a dummy module name; `browser_resize` did work for the 820px drawer check this time.

## Info tips + Facility notes (Oct 2026)

- **Help/description text goes in an "i" popover, not in a grey line under the title.** Shared component: `<button type="button" class="info-tip-btn" aria-label="..." data-bs-toggle="popover" data-bs-trigger="hover focus" data-bs-placement="bottom" data-bs-content="...">i</button>` (`.info-tip-btn` is defined once, in `theme.css`). It is started by the top-level `initInfoTips(root)` in `app.js` (already called by the Audit and Administration handlers - call it after rendering any new fragment that has one). If JS changes the text later use `setInfoTipText(el, text)` (a popover caches its content); and don't put the button *inside* an element whose `textContent` JS rewrites (e.g. `#facility-form-title`) - put it beside it.
- Applied so far: Audit & Reports, the **Facility** tab (list subtitle, the three form section descriptions, the Create/Edit hint `#facility-form-hint`) and the **Specialties** tab (list subtitle, "Discipline Details", Create/Edit hint `#specialty-form-hint`). The user wizard and Roles tabs still show their grey descriptions; the Specialties per-row descriptions (the specialty's own data) and the "Machine key..." field hint also stay visible. A form title that JS rewrites sits in `.admin-title-row` next to its tip (this class was `fac-title-row` for a day).
- **Specialty Code** (`specialties.code`, e.g. `SPEC-CARD`) is hidden from the Specialties *list* (still in the Add/Edit form and saved); the list has 5 columns, so its loading/empty/error `colspan` is 5 (the Facility list is 6).
- **Facility Code** (`facilities.facility_code`, e.g. `FAC-APH-01`): short internal id, auto-generated on create when left blank; hidden from the facility *list* on request, still in the Add/Edit form and used in the staff "Facility" dropdown label. **Facility Type** (`facility_type`: Clinic / Hospital / Specialty Center / Outpatient Center / Other): a plain label shown in the list - no billing/scheduling/permission logic reads it.

## Roles & permissions (Oct 2026) - roles only, enforced on the server

- **Five staff roles** (`users.role` ENUM, + reserved `Patient`): Super Admin, Doctor, Nurse, Receptionist, Billing Staff. **The Therapist role was removed** (decision of the owner; the cardiology build has no such role). **No per-user permission overrides**: a person's access is exactly their role's access. Owner decisions: Billing Staff sees **billing codes only, never clinical notes**; **no Compliance role** (compliance work = Super Admin); Practice Manager / Office Manager / IT Admin / Compliance Officer / any "Administrator" user type still map to **Super Admin** (revisit - least privilege would split a non-clinical admin role from it); Physical Therapist maps to Doctor; Psychologist job role removed.
- **`App\Security\Roles` (`backend/app/Security/Roles.php`) is the single source of truth**: constants `ALL_STAFF`, `ADMIN` (Super Admin), `PROVIDER` (SA + Doctor), `CLINICAL` (SA + Doctor + Nurse), `CARE_COORDINATION` (CLINICAL + Receptionist), `BILLING_TEAM`, `BILLING_VIEW`, and `Roles::enforce($group)` (401 without a session, 403 for the wrong role, then exits). Use them - **never type role names into a controller**. New endpoint that returns/changes PHI = call `Roles::enforce(...)` (or the controller's `checkAccess(Roles::X)`) before touching data. The legacy names `Admin`/`Staff`/`Therapist` must not appear in any role list.
- **Access matrix (enforced)**: Admin screens, settings, roles, audit log, **deleting a patient** = Super Admin only. Clinical notes read/write/documents/allergies/problems/medication list/order list+results = Super Admin, Doctor, Nurse. Note delete, sign/lock/addendum, prescribe, place order, review/sign a result = Super Admin, Doctor. Referrals, recalls, intake forms, appointments (edit), telehealth sessions = + Receptionist. Invoices/claims/payments = Super Admin + Billing Staff (Doctor can view). Receptionist and Billing Staff **cannot read clinical data**; the Encounters queue hides the chief complaint from both; the notification bell shows intake/referral notices only to `CARE_COORDINATION`. Billing gets codes from `BillingController::encounterCharges` (encounter ref, patient, date, provider, ICD-10/CPT lines - no narrative).
- **`AuthenticationMiddleware` re-reads `users.role` + `is_active` on every request** (one PK query): deactivating/deleting a user ends their session on the next request and a role change applies immediately (it used to apply at next login).
- **Patient chart tabs follow the role** (`chartTabsForRole()` in app.js, display only - the server is the real gate): Receptionist = dashboard, demographics, appointments, messages, referrals, recalls; Billing Staff = dashboard, demographics, appointments, messages, billing; everyone else all tabs.
- **One definition of who-can-do-what: `Roles::AREAS`** (same file). Each area (patients, encounters, orders, medications, billing, admin_users...) lists, per action (view/create/edit/delete), the role-group constant the controllers enforce with. **`GET /api/me` -> `user.permissions`** (`Roles::currentPermissions()`, booleans; the UI gates buttons with `userPerms?.patients?.edit` etc. - keys `patients`, `admin_users`, `admin_roles` are read by app.js) and **`GET /api/roles/matrix`** (Super Admin only) are generated from it. **To change a BUILT-IN role's access: edit the controller's `Roles::enforce/checkAccess(...)` group AND the matching `AREAS` entry together** (CLI test `rbac_matrix_test` compares controllers against the intended matrix). The wizard is **4 steps** (Personal, Role & Type, Practice Assignment, Review & Create); Review shows the system role (`staffSystemRole()` mirrors `UserController::resolveAssignableRole`, display only).
- **Custom roles (enforced, Oct 2026):** Roles & Permissions tab -> *Add Custom Role* (Super Admin). A custom role = name + description + **base role** (Doctor/Nurse/Receptionist/Billing Staff, never Super Admin) + per-area View/Create/Edit/Delete ticks in `custom_roles.permissions_matrix`. **It can only NARROW its base role**: effective access = base role's access AND the ticks (`Roles::sanitizeMatrix` clamps ticks to the base ceiling on save, create/edit/delete imply view; admin-only cells can never be ticked). A user is assigned one in the wizard's **Access Role** select -> `users.custom_role_id`, and `users.role` holds the base role (so scoping, specialty-required, dashboard blocks, chart tabs all follow the base role). **Enforcement is central, not per controller:** `AuthenticationMiddleware` re-reads the user + joined custom role on every request (edits/reassignments apply on the next request), sets `$_SESSION['custom_perms']`, and for custom-role users checks `RouteAreas::resolve(method, path)` (path -> area, HTTP method -> action, regex overrides for POSTs that edit): unticked = 403, **an unmapped route is denied (fail closed)** and a user pointing at a deleted role gets nothing but neutral routes (`/api/me`, logout, change-password, notifications, providers). **When you add an API route, add it to `RouteAreas::RULES`** (the scratch route-coverage check lists unmapped ones). The role's base role is locked while users are assigned, and a role with users can't be deleted (409). The Roles tab is a **matrix** (owner-supplied design): role pills with icons, search box + legend, collapsible groups, one row per area with icon, and View / Create / Edit / Delete cells drawn as coloured squares (**green = full access** i.e. everything the base role can do there, **blue = limited/view only**, empty = none, grey = not available for the base role). Custom roles click the squares (create/edit/delete turn View on; turning View off clears the row); built-in roles are read-only. There is deliberately **no Export column** - no export permission exists on the server; do not add the column without a real, enforced export area. Earlier switch and segmented-button versions were dropped. Styles: `.rbac-cell*`, `.rbac-toolbar`, `.rbac-legend`. and the **Delete role** button is always shown for a saved custom role but disabled (with a tooltip) while users are assigned. Table `custom_roles` is created (never seeded) by `bootstrap/app.php`; the old tables `rbac_policies` and `users.custom_permissions` stay dropped.
- **Found, not fixed**: `BillingController::encounterCharges` invents a default line (Z00.00 / 99213 / $100) when an encounter has no codes - against the "never invent a code" rule; Receptionist is scoped to its own/unassigned recalls (provider-scoped list) which makes the front-desk recall view nearly empty; the "Clinical Psychologist" option in the provider-classification dropdown (that field is not saved anyway); `.athena-template-card` / `.athena-perm-*` CSS in administration.css is now unused; custom-role users have no UI hiding by permission beyond `permissions` button gating (the sidebar still follows the base role - the server blocks the rest).
- **Testing roles without logging in**: the controllers can be called from a CLI script with a stubbed `$_SESSION` (point `AuditLogger::$logTable/$headTable` at scratch tables so the real audit log stays clean) - call only safe endpoints for allowed roles (reads, or writes with empty input that fail validation) and assert 403 for the others.

## Visit types (Oct 2026) - one cardiology list

- **The visit types live in ONE place: `App\Support\VisitTypes::LIST`** (name => default appointment minutes): New Patient Consultation 45, Follow-Up Visit 20, Urgent Cardiology Visit 30, Post-Hospital Follow-Up 30, Post-Procedure Follow-Up 30, Medication Management 20, Preoperative Cardiac Evaluation 40, Cardiology Consultation 45. To add or rename one, edit that file only. `GET /api/visit-types` (any signed-in staff; neutral in `RouteAreas`) serves it; the front end loads it with the top-level `loadVisitTypes()` and builds options with `visitTypeOptionsHtml(selected)` - **never hard-code visit-type `<option>`s again** (it was hard-coded in 6 places, with different values in each). The two selects in static page HTML (`#encounter-visit-type` in `clinical_modal.php`, `#enc-wi-visit` in `encounters.php`) start empty and are filled by `applyVisitTypeSelects()` after every module load.
- **Server validation** (`VisitTypes::resolve()`): a booking (`CalendarController` store/update), a walk-in encounter (`EncounterController::start`) and a saved note (`ClinicalController`) must use a listed type (400 otherwise); empty = `Follow-Up Visit` (the old default `Family Care` is gone). **An unchanged old value on an existing row is tolerated** so old records stay editable (the dropdowns keep it as an extra option; `encounter_lifecycle.js` does the same for the encounter form), and a stale page sending `New Patient` / `Follow Up` / `Cardiology Consult` is mapped to the new name. Starting an encounter from an appointment copies the appointment's type.
- **Default length:** choosing a type pre-fills the appointment duration in the schedule popup (`visitTypeMinutes()`), only until the user types a length themselves and never when editing. The old cardiology-only "slot types" (Echocardiogram, Stress Test, Holter Monitor, ECG, Cardiology Consult) were removed from the dropdown - they are tests (Orders & Labs), not visits.
- **Data:** old values were mapped in the live DB (New Patient -> New Patient Consultation, Follow Up -> Follow-Up Visit, Cardiology Consult -> Cardiology Consultation). **`Stress Test` (2 appointments, 2 encounters) was deliberately left as it is** - it has no equivalent in the list; ask the owner before changing it. Not built (not asked): urgent badge/sorting, per-type encounter sections, per-type billing codes.

## Login & session conventions (Oct 2026)

- **Lockout:** 5 wrong passwords on a real, active account lock it for 15 minutes (`users.failed_login_count`, `locked_until`, MySQL `NOW()` clock, constants in `AuthController`). A locked account refuses even the correct password. **Unknown user, wrong password, inactive and locked all return the same message and 401**, and an unknown username still costs one bcrypt verify (dummy hash), so neither the text nor the timing reveals which usernames exist. Success resets the counter. Super Admin sees a **Locked** badge in User Management and an **Unlock** button (`PUT /api/user/{id}/unlock`, audited); an admin password reset, a reset-link reset and a password change also clear the lock. Audit lines: `Account Locked - Too Many Failed Logins`, `Login Refused - Account Locked`.
- **`session_regenerate_id(true)` runs at login** (session fixation), and again when the user changes their password.
- **Changing/resetting a password ends the user's OTHER sessions:** `users.password_changed_at` is stamped; the session remembers `$_SESSION['pw_at']` from login and `AuthenticationMiddleware` (which already re-reads the user row every request) signs out any session whose `pw_at` differs. The session that made the change gets the new stamp.
- **`App\Security\PasswordPolicy::check()` is the one password rule**: >= 10 characters, a letter and a number, not a common password, not containing the username or the email's first part, not equal to the current one. Used by change-password, reset-password and the admin's user create/edit. The wizard/change/reset pages mirror the first part via the top-level `passwordRuleProblem()` in app.js (the server is the real check); the wizard's "Generate password" always includes a letter and a number. Old passwords stay valid until changed. The login form never applies the policy.
- **Forgot password = emailed one-time link.** `POST /api/auth/forgot-password` (public, rate limited) always answers the same generic text; only an active user with an email gets a link (token = 32 random bytes, only its SHA-256 stored in `password_resets`, valid 30 min, single use, a newer link voids older ones, max 3 per hour per account and per IP; link built with `AppUrl::publicUrl`). `POST /api/auth/reset-password` claims the token atomically, applies the policy (a weak password keeps the link valid for another try), clears must-change/lock. Pages: `#forgot-password` and `#reset-password?token=` (`modules/forgot_password.php`, `reset_password.php`). **Public pages are listed in two places that must agree:** `Router.handleRouting` (`publicPages`) and `ApiService.onPublicPage()` (otherwise the signed-out `/api/me` probe bounces the visitor to #login). Note `app.js` imports `./api.js` unversioned, so after editing api.js a plain reload can serve the old copy - hard-reload.
- **No "Remember me"** (removed on purpose: no long-lived sessions for patient data). Idle timeout stays 15 min.
- **`RateLimitingMiddleware`** writes `storage/rate_limits.json` under `flock` (parallel requests used to overwrite each other); it protects login and the two reset endpoints (100 requests/minute/IP) - the per-account lockout is the real brute-force defence.
- **Seeded demo accounts:** the old passwords documented in `schema.sql` were removed from the comment; `dr_smith` and `billing_staff` (still on those defaults) were forced to change their password at next login (`must_change_password=1`). Any new environment: set a new password for every seeded account.
- **Open / not done:** the session fingerprint is `md5(IP + User-Agent)` (a user whose IP changes, or many users behind one proxy, are affected); no two-factor login; no list of active sessions; `cookie_secure` must be switched on and HSTS reviewed when the site moves to HTTPS. Tests for the reset email use a stub `EmailService` (never real mail); HTTP login tests write real audit lines for the scratch user (the audit table is append-only).

## Audit log conventions (Oct 2026)

- **Always write through `AuditLogger::log($userId, $username, $role, $patientId, $actionType, $module, $recordId)`** - never `INSERT/UPDATE/DELETE audit_logs` yourself. Argument meaning matters: `$role` is the *actor's* role (never the action text), `$patientId` is **only a patient id** (put user/facility/role/claim ids in `$recordId`), `$actionType` is short readable text, `$module` is the app area (`Billing`, `Administration`, ...). The old 3-argument "shorthand" form was removed. Typical call: `AuditLogger::log($_SESSION['user_id'] ?? null, $_SESSION['username'] ?? null, $_SESSION['user_role'] ?? null, $patientId, 'Update Patient Record', 'Patient Directory', (string)$id)`.
- **What must be audited:** sign-in/out and failures, and every *read or change of patient data* (opening a chart/note/invoice/result/message/referral/intake, edits, deletes, exports, downloads) - one line per request, with the patient id when known. List/search screens log one line without a patient id. If you add an endpoint that returns PHI, add its `AuditLogger::log`.
- **The table is append-only and tamper-evident.** `audit_logs` has BEFORE UPDATE/DELETE triggers (they reject changes - so test data **cannot** be cleaned up; tests must use scratch tables, see below), **no foreign keys** (deleting a user/patient must never touch audit rows - ids stay as plain integers), `timestamp` is a **UTC** `DATETIME` set by the logger, and `log_hash = HMAC-SHA256(key, canonical JSON incl. prev_hash)` with the key derived from the encryption key. `audit_chain_head` (1 row, locked `FOR UPDATE` while writing) serialises writers and lets verification catch deleted *tail* rows. Every field is clipped to its column length **before** hashing (sql_mode is empty, MySQL would otherwise truncate silently and the hash would never verify). A rolled-back caller transaction also rolls back its audit line (the logger joins the caller's transaction via a savepoint).
- **A failed audit write is never silent:** `error_log` + `storage/audit_failures.log` (no PHI); the count is shown on the Audit screen.
- **Audit & Reports (`#reports`, `AuditController`) is Super Admin only** - enforced server-side on `index`/`verify`/`export` (403 otherwise) and the nav item is hidden for other roles. Features: filters + paging, per-row patient name (decrypted only for the page being shown), **Verify now** (`/api/reports/audit/verify` recomputes the whole chain and checks the head), CSV export (patient ids only, spreadsheet-formula-safe, `fputcsv` needs the explicit `escape` argument on PHP 8.4+). Opening the log, verifying and exporting are themselves audited. All log values are rendered with `calEscape` (failed-login usernames are attacker-typed text).
- **Honest limits:** MySQL `root` (which the app uses) can still `DROP TRIGGER`/`TRUNCATE`; real immutability in production needs a non-root application DB account (no `DROP`/`ALTER`/`TRIGGER`) - not done yet. The page says "tamper-evident, append-only", not "immutable". The HMAC key derives from the (still hard-coded) encryption key in `config/security.php`; rotating that key makes old entries unverifiable.
- **Testing the logger/controller:** `AuditLogger::$logTable` / `$headTable` are a test seam - point them at scratch tables (`CREATE TABLE x LIKE audit_logs` + a head row + the two triggers), run, then drop them. Never write test rows into the real `audit_logs`.
- **Fixed alongside:** `GET /api/referrals/{id}/document` had no authentication at all (anyone could download a referral file by id) - it now requires a login; the unused `/api/dashboard/recent-activity` (returned patient names to every role) was removed.

## Why

These rules came out of real mistakes/near-misses across sessions: a naive placeholder-count script producing a false positive, a stale-schema.sql assumption almost causing a live/documented drift, the discovery that encrypted PII columns can't be matched with a plain `WHERE` (which is why the blind-index pattern exists), a duplicate CSS class definition silently forcing every status badge in the app to a fixed 180px width, and — most severe — a route-scoping mistake that meant every real encounter save had been silently failing (false "Chief Complaint is required" error) for every specialty, discovered only while live-verifying the new Cardiology workflow's save/reload round-trip. Following them isn't optional busywork — skipping them is how the bugs above happened the first time.

## Insurance claims workflow (Sept 2026)

- **`ClaimController`** owns claims (`insurance_claims`, `claim_lines`, `claim_status_history`, `insurance_payers`). Lifecycle: Draft -> Ready (readiness checklist must pass) -> Submitted -> Accepted | Rejected -> remit -> Paid / Partially Paid / Denied; Denied -> Appealed -> remit; any open claim can be Closed (move balance to patient, or write off). Transitions are validated server-side (`TRANSITIONS`, remit/appeal/close/reverse have their own endpoints) and every one writes `claim_status_history` + the audit log. The server also returns the allowed `actions` for the current status/role; the UI only renders what it is given.
- **Money always flows through the ledger:** posting a remittance inserts an insurance `payments` row (source Primary/Secondary Insurance, `claim_id` set) and a Contractual `adjustments` row, then calls `BillingController::recalcInvoice()`. **Insurance payments can't be voided from the invoice** - use *Reverse Remittance* on the claim (voids both rows, claim back to Submitted; blocked while a non-closed secondary claim exists). Invoice statuses `Awaiting Insurance` (an open claim exists) and `Patient Balance` (insurance finished, balance remains) are set by `recalcInvoice`, never by hand.
- **Per-line remit rules:** denied line (denial code) = nothing paid; otherwise `allowed <= charge`, `paid <= allowed`, adjustment = charge - allowed, patient resp = allowed - paid. The remit can't exceed the invoice balance. Invoices with a discount can't be billed to insurance.
- **Secondary billing:** `bill-secondary` creates a Secondary claim (charge per line = the primary's remaining patient responsibility, `parent_claim_id` set). The 837/CMS-1500 for a secondary claim rebuild the *original* line charges and the primary payer's paid/adjustment from the parent claim's lines.
- **Coverage** comes from `patient_insurance` (`insurance_type` Primary/Secondary; `primary_provider` holds the *payer name*) and is snapshotted into `insurance_claims.coverage_json` at creation. Payer ID codes and claim filing type live in `insurance_payers` (seeded blank - the clinic must enter real payer IDs). Provider NPI/taxonomy come from `users`, facility NPI/TIN/address from `facilities`; 837 submitter/receiver IDs from `system_settings` (`billing_submitter_id`, `billing_receiver_id`, `billing_contact_name/phone`).
- **Exports:** `Claim837Generator` (pure function, 5010 837P, primary + secondary, self/dependent) and the CMS-1500 *data sheet* (HTML laid out by box number, not the red-ink form). The 837 has only been structure-checked (SE count, amounts sum) - **never validated against a real payer/clearinghouse**; run it through the clearinghouse's validator first. Downloads are audit-logged; PHI is never written to logs.
- **UI: the claim is a page, not a popup.** Inside the Insurance Claims tab three views toggle via `showClaimsView('list'|'claim'|'payers')`: the list (`#claims-view-list`), the claim workspace (`#claims-view-claim`, filled by `renderWorkspace()`) and Payers & settings (`#claims-view-payers`). There are **no claim/payer modals**. Workspace = header (claim, status, ONE primary next-action button from `nextAction()`, a **More** dropdown for secondary/manual actions) + money strip + a 5-step stepper (Eligibility, Generate 837, Validate, Send, Remittance) that shows **one step's pane at a time** + a sticky collapsible summary (coverage, provider, lines, ledger, history, EDI files). The stepper auto-selects the next actionable step (`autoStep`) after each action; Edit claim and the manual action forms (submit/accept/reject/remit/appeal/reverse/close) render **inline in the main pane** via `claimPanelHtml`/`wireClaimPanel`. The validator's payer/submitter **Fix** opens the in-page Payers view with a back-to-claim link; patient/provider/facility Fix opens a new tab. The invoice viewer stays a modal; its Create Claim switches to the Claims tab and opens the workspace (`window.openClaimDetail`). Styles are `clw-*` (workspace) and `clm-*` (shared bits); the old modal-era `clm-step/issue/money/...` rules were deleted - grep before adding a class. Generate Invoice has a "Bill to" select defaulted from `GET /api/billing/patient/{id}/coverage` and blocks Insurance when the patient has no coverage.
- **Fixed while building this:** `storeInvoice()` looped over line items by reference without `unset($item)`, so the last line was overwritten by the previous one (invoice `INV-00001` still carries that corrupted duplicate line - its total is right, the second line's CPT/description are lost).
- Test data: `[ZZTEST]` in invoice `notes` / insurance `plan_name`; clean up with a scratchpad script (claims cascade lines/history; payments/adjustments/invoices deleted explicitly).
- **AR aging (`GET /api/billing/ar-aging`, panel at the top of the Claims tab):** 0-30 / 31-60 / 61-90 / 90+ buckets in two rows. *Insurance* = open claims (`billed - insurance_paid - adjustments`), aged from **date of service**; *Patient* = invoices with a balance not waiting on insurance (Issued / Partially Paid / Patient Balance / Overdue), aged from **invoice date**. The older manual actions (Mark Submitted/Accepted, Post Remittance, Download 837) still exist as a fallback.
- **Nothing is live yet: `system_settings.clearinghouse_mode = 'simulator'`.** `Clearinghouse\SimulatorClearinghouse` plays clearinghouse *and* payer and speaks real X12 (270/271, 999, 277CA, 835) behind `ClearinghouseInterface`; `ClearinghouseFactory` returns it and refuses any other mode. Its adjudication (80% allowed, deductible capped at half the allowed total, copay, 20% coinsurance; scenarios Auto/Paid/Partially paid/Denied/Rejected, Inactive for eligibility) is **illustrative, not any real payer's logic**. Going live = add one class implementing the interface (needs an Availity account, credentials, real payer IDs); the validator, parsers and UI stay as they are. Simulator screens carry a "SIMULATOR" badge.
- **Send is gated server-side** (`ClaimEdiController::send`): readiness checklist passes, eligibility is Active and <= 7 days old, and the 837 is **re-generated and re-validated at send time** (an old validation is never trusted). Only Draft/Ready/Rejected claims can be sent; a 999/277CA rejection sets the claim Rejected with the reason so it can be fixed and re-sent.
- **`Claim837Validator` validates the generated file text**, not the source data (integrity, required elements, balancing, code/format incl. NPI Luhn check). Every issue names the field to fix; `fix.target` tells the UI where (claim Edit panel / Manage Payers / other screens opened in a new tab). It is a subset of SNIP levels and **not a substitute for the clearinghouse's own edits**. `tests`: mutation-tested (35 single-fault mutations each raise their code; clean primary and secondary+dependent files pass).
- **835 handling:** `Claim835Parser` parses + `describeForClaim` reconciles (BPR total = CLP paid = sum of SVC paid, charge = paid + patient resp + contractual per paid line). It is received first (`insurance_claims.pending_835_tx_id`, shown, not posted) and only posted on the user's confirmation through `ClaimController::applyRemit()` - the **single money path shared with the manual remit form**. A line is "denied" when it is paid 0 with a non-cost-sharing CARC (not 1/2/3/45 and not group PR). A posted 835 can't be posted twice; reverse via *Reverse Remittance*.
- **EDI files contain PHI:** stored **encrypted** in `edi_transactions.content_encrypted` (EncryptionService), returned only to authenticated users via `GET /api/billing/claims/{id}/edi/{tx}`, every view/download audit-logged without content. `edi_transactions` / `eligibility_checks` have **no FK to claims** - delete them explicitly when removing test claims.
- **Seed data note:** the seeded facility NPI (`1487293840`) fails the NPI check digit, so the validator (correctly) flags it until it is corrected under Administration > Facilities. Provider NPI/taxonomy, 837 submitter/receiver IDs and payer IDs must also be filled in before a claim can be sent.
- **Edit Claim can fix the diagnosis:** an invoice built from an encounter with no ICD-10 produces claim lines without one, which the validator flags (`HI_MISSING`, `DX_POINTER_MISSING`). *Edit Claim* now has an ICD-10 field per line (`PUT /api/billing/claims/{id}` accepts `icd10_code`); a line with a diagnosis but no/out-of-range pointer is pointed at its own diagnosis automatically. The claim's line is edited, not the invoice line.
- **Testing note:** the app sends `X-Frame-Options: DENY`, so narrow layouts can't be checked in an iframe, and Playwright's `browser_resize` is unreliable in this browser (it reported a 2304px viewport and once reset the page to about:blank). Check responsive rules by re-scoping the `@media` blocks to a fixed-width wrapper in `browser_evaluate`.

## Encounters module conventions (Sept 2026)

- **`#encounters` is the clinical work queue** (`public/modules/encounters.php`, `initEncountersHandler()` at top level of app.js, `enc-` CSS prefix in `css/modules/encounters.css`). One row per visit; the **stage is derived server-side** in `EncounterController::queue()` (never stored): Scheduled → Checked in → In progress → Ready to sign → Signed → Billed. Chips show per-stage counts (stage filtering is client-side so counts stay complete).
- **Lifecycle:** Check in = `PUT /api/appointment/{id}/status` `Arrived` (Receptionist+clinical). `POST /api/encounters/start` (`{appointment_id}` or walk-in `{patient_id, provider_id?, visit_type?}`; Super Admin/Doctor/Nurse) creates the note **linked to the appointment**, is idempotent, and sets the appointment `In-Progress`. `uniq_note_appointment` on `clinical_notes.appointment_id` is the DB backstop. Signing (`ClinicalController::signAndLock`, Super Admin/Doctor only) sets the linked appointment `Completed` and `billing_queue_status=pending_review`.
- **Billing only lists signed encounters** (`unbilledEncounters` requires `cn.lock_state = 1`). Unsigned drafts never reach Billing; don't bulk-sign existing records to "fix" an empty list.
- **The encounter form only renders inside the patient chart.** The tabbed form (Chief Complaint, Vitals, Assessment, Billing, Sign…) comes from `clinical-tabs.js`'s `populateEncounterModal` override, which only runs while `#patient-dashboard-full-content` is visible; the plain `#clinical-encounter-modal` has no chief-complaint input. So any route that shows an encounter goes through `window.openEncounterInChart(patientId, noteId)` (top level in app.js), which opens the chart and clicks the chart's own Edit button (calling `populateEncounterModal` directly races the chart render). `encounters.php` deliberately does **not** include `clinical_modal.php`.
- **"Signed" means `lock_state = 1`, nothing else.** `signed_by_name`/`signed_signature_data` are also written by a plain draft save, so the chart's Signed (Locked) state and the queue's signed-by label both key off `lock_state`. The Sign tab's **Sign Encounter** button saves, then calls `POST /api/clinical/notes/{id}/sign` (before this it only saved and nothing on the chart could lock an encounter).
- **Sign validation counts diagnoses from `patient_problems`** (Active/Chronic with an ICD-10) as well as `icd10_codes`; in the tabbed UI `icd10_codes` only carries the CPT billing lines, so requiring it alone made a diagnosis-only note unsignable.
- **Arrived opens the SOAP form.** Whenever an appointment becomes `Arrived`, call the top-level `window.openEncounterForArrival(appointmentId, patientId)` (app.js, next to `openEncounterInChart`): it calls `/api/encounters/start` (linked, idempotent) and then `openEncounterInChart`. Hooked in three places: the Calendar appointment-details status save, the schedule/edit popup (only when the status *changed* to Arrived on a single appointment - `POST/PUT /api/appointment` now return `appointment_id`, and `created_count` for POST), and the Encounters queue **Check in** button. Deliberately not hooked: the Waiting List confirm popup and recurring series. Roles that can't start encounters (front desk) get the check-in plus a toast, no navigation. Any new place that sets Arrived should use the helper, not its own start/open code.
- `openEncounterInChart` shows a full-screen "Opening encounter..." cover (`#enc-open-overlay`) for the whole Patients -> chart -> Encounters list -> form transition (the form is only reachable by clicking the list's Edit button, see above) and removes it in `finally` once the form has painted; keep any new step of that flow inside the same try/finally so the cover can never get stuck (20s fail-safe too).
- `openPatientChart(p, defaultTab)` defaults to the `dashboard` tab; pass `'encounters'` when the encounter list/form is needed (`openEncounterInChart` does).

## Cardiology encounter workflow C01-C14 (Oct 2026)

- **The encounter form's screens are ONE keyed list: `tabSpecs` inside the `populateEncounterModal` override** (`clinical-tabs.js`, near the bottom). Each entry is `{ key, label, build, only? }` in the order the clinician walks the visit; `only: 'cardio' | 'ortho'` drops a screen for other specialties. **Add or reorder a screen only there.** Anything that needs a particular screen looks it up by key (`indexOfKey('billing')`), never by number - the Billing CPT lazy-load and the Sign provider refresh were hard-coded as `i === 8` / `i === 9` and would silently point at the wrong pane the moment a screen was inserted.
- **Never hard-code a pane's neighbour.** Each `cpB_*` builder still writes its own `.cp-nav` with a "&larr; Previous" and a "Next &rarr;" button, but `wireWorkflowNav()` (called right after `wireAll`) re-points and relabels them from the live tab order, and hides them on the first/last screen. Buttons are matched on their label (starts with "next" / contains "previous"), so Save Draft / Clear / View Results in the same `.cp-nav` are untouched. A new pane just needs a `.cp-nav` with those two labels and it joins the chain.
- **The owner's exact order is live: C01 Visit Details, C02 Chief Complaint & Cardiac Symptoms, C03 Cardiac HPI, C04 Cardiac History, C05 Medications & Allergies, C06 Vitals, C07 Examination, C08 Cardiac Assessment, C09 Diagnosis / Problem List, C10 Diagnostic Orders, C11 Results Review, C12 Treatment & Plan, C14 Summary & Sign.** C13 Follow-up is still not built (no existing UI to relocate - needs the `patient_recalls` wiring, still pending). Ortho is interleaved at its old relative position (after Examination) and stays one pane - it was not asked to be split the same way as cardiology.
- **Pane ids run `cpP0`-`cpP14`** (cpP8 reused for Cardiac HPI, cpP9 reused for the merged Medications & Allergies pane, cpP10 reused for the split-out Diagnosis List, cpP14 new for Results Review) and the cleanup loop in the override removes `cpP0..cpP15` before each render (one id of headroom) - **raise that bound when you add a pane id**, or a stale pane survives and can steal the real `#cardio-form` out of the hidden modal.
- **The mega `#cardio-form` (clinical_modal.php) was split into 12 sections, each `id="cardio-sec-*"`, distributed across six different panes.** `CARDIO_RELOCATION` (clinical-tabs.js, just above `cpB_CardiacHPI`) is the ONE place that says which section goes to which pane's mount point (`cpHpiMount`, `cpVitalsCardioMount`, `cpExamCardioMount`, `cpAssessCardioMount`, `cpResultsMount`, `cpPlanCardioMount`) - add a row there, never an ad-hoc `appendChild`, if a section needs to move again. `relocateCardioSections()` runs once per render, only for a cardiology encounter, right after the panes (and their mount points) exist.
  - **Every control inside a relocated section carries an explicit `form="cardio-form"` attribute** (57 of them). Not cosmetic: per the HTML living standard, moving a form control out of its `<form>` ancestor drops its form association - and therefore drops it from `new FormData(document.getElementById('cardio-form'))`, which is exactly how `cardio_data` is built in `submitEncounter` - unless the control carries that attribute, which keeps it associated wherever it physically lives in the DOM. Verified: filling one field in each of the 6 target panes and running the real extraction produces all 57 keys.
  - **Rescue sections back inside `#cardio-form` BEFORE the `cpP0..cpP15.remove()` cleanup runs**, same reason as the pre-existing whole-form rescue right below it: otherwise the cleanup deletes the real fields along with the stale pane currently holding them. `CARDIO_SECTION_IDS` (derived from `CARDIO_RELOCATION`) is the rescue list. Verified stable across 3 consecutive re-renders of the same encounter (57 fields, 0 duplicates, every time).
  - **`toggleCardioWorkflow()` (app.js) is scoped from `document`, not `cardioForm`.** Every relocated section is still a `[data-workflow]` block, but none of them are descendants of `#cardio-form` once relocated - a `cardioForm`-scoped query would silently find none of them and the 5-pathway show/hide (chest_pain/dyspnea/palpitations/hypertension/followup) would stop working for every relocated section. Verified across all 5 pathways.
- **C01 Visit Details (`cpB_VisitDetails`, cpP12):** read-only visit facts from the note, plus the only two editable fields, **referring provider** and **reason for referral** (`clinical_notes.referring_provider` / `referral_reason`). House pattern: visible input in the pane -> hidden `#referring-provider` / `#referral-reason` in `clinical_modal.php` -> `submitEncounter`. SQL uses `IFNULL(?, col)`, `app.js` sends `?? null` - **a save from a screen that doesn't render these inputs leaves them alone instead of blanking them**; sending `''` still clears them deliberately.
- **C02 Chief Complaint no longer duplicates C03.** `cpB_CC` branches on `note.encounter_type`: a cardiology encounter gets a short list of quick triage flags (Chest Pain/Dyspnea/Palpitations/Syncope/Edema/Fatigue/Dizziness/Orthopnea) and no free-text HPI box, with a note pointing to C03 for the full OPQRST history; a non-cardiology encounter (no C03 of its own) keeps the original generic symptom checklist + free-text HPI unchanged. Same `.cpSym`/`#ros`/`#hpi` ids and wiring either way - `wireAll`'s `if (cpHPI && rHPI)` guard already tolerates the field not existing.
- **C04 Cardiac History (`cpB_CardiacHistory`, cpP13, cardiology only):** patient-level, **not** encounter-level - `patient_cardiac_profile`, one row per patient, upserted by `CardiacProfileController` and stamped `last_reviewed_at`/`by`. **Reviewed each visit, not retyped**, and exists so the cardiac risk scores (ASCVD, CHA2DS2-VASc, HAS-BLED) have structured inputs instead of prose. Field names live once in `CardiacProfileController::FIELDS` (server) and `CP_CARDIAC_CONDITIONS`/`CP_CARDIAC_RISK`/`CP_BLEEDING_RISK`/`CP_CARDIAC_DATES` (client) - keep those in step. Saves through its **own** button and endpoint, not the encounter save. Conditions that are also problem-list items still belong in `patient_problems` with their ICD-10; this table is the risk-factor view, not a replacement.
  - Routed as `GET|PUT /api/clinical/cardiac-profile/{patient_id}` **on purpose**: the existing `#^clinical/#` rule in `RouteAreas` maps it to the `encounters` area, so custom-role users get the clinical-only gate with no new rule. A new endpoint outside `/api/clinical/` needs its own `RouteAreas::RULES` entry or custom roles get 403 (fail closed).
- **C05 Medications & Allergies merges the old two separate panes into one** (`cpB_MedsAllergies`), same ids (`cpAddMedReal`/`cpMedRealBody`/`cpAddAlgReal`/`cpAlgRealBody`), two cards on one screen - no `wireAll()` changes needed, only the markup merged. Its stray `cpPrA`/`cpNxA` nav wiring (the old standalone Allergy pane's ids) was removed from `wireAll` since that pane no longer exists; if `wireAll` ever throws "Cannot set properties of null" again after a future pane merge/split, this is the failure class - grep `wireAll` for `getElementById('cpXxx')` and cross-check every id still exists in the current `tabSpecs`.
- **C09 Diagnosis / Problem List is split out of C08 Assessment** (was one combined pane) - same `patient_problems` table, same `cpAddDiagReal`/`cpDiagRealBody` ids, so `loadAssessmentDiagnosisList()` needed no changes, only the markup moved.
- **Signing works** - verified end-to-end (refuses without a diagnosis, signs with one, locks, routes to Billing, refuses a second signature, refuses a Nurse). The "0 signed notes" in the database is disuse, not a bug; the broken `.diag-row-item` selector noted in older docs is already fixed.
- **`clinical-tabs.js` is CRLF** (`\r\n` throughout, consistently) - a plain-`\n` multi-line string match against it will silently find nothing. Scratch scripts that edit it should normalize to `\n` for matching and convert back to `\r\n` before writing. (This is also why a shell `node -e` one-liner with backtick template literals inside it is extra dangerous here - the shell can silently eat the backtick-quoted parts; write the script to a file instead for anything beyond a one-line replace.)
- **Still to build (C01-C14 plan, phases 2-4):** C11 Results Review's structured ECG/Echo/Holter/device/labs fields write into `cardio_data` (not the real, still-empty `results` table - that full order->result->review loop is Phase 2), C13 Follow-up (`patient_recalls` works but no encounter writes it), C10's cardiology order catalog, C05 medication reconciliation (`med_rec_done_at` column added, unused), C08 risk calculators (ASCVD has a Calc button; CHA2DS2-VASc/HAS-BLED not built), C12 `treatment_plans` / `patient_education` (both 0 rows), C14 note preview + completeness checklist.

## Telehealth conventions (Oct 2026)

- **Booking a Telehealth appointment** (`CalendarController` store/update) calls `TelehealthController::createAndSendForAppointment($apptId, $patientId, $providerId, $start, $end)`. It keeps **one Active `telehealth_sessions` row per appointment**: re-saving with the same times does nothing (no new room/email); changed times update `scheduled_start/end` and send an "Updated: ..." email; a new appointment creates the room and emails the patient. Ad-hoc invites from the `#telehealth` page have NULL schedule (ungated).
- **The patient email links to our `join_url` (`public/telehealth_join.php?room=`), never straight to meet.jit.si** - otherwise the time gate is bypassed.
- **The 5-minute gate is enforced server-side** by the public `GET /api/telehealth/join-check?room=` (`TelehealthController::joinCheck`, `JOIN_EARLY_MINUTES = 5`): states `too_early | open | ended | invalid`, timing only, no PHI. "Now" is MySQL `NOW()` (the same local clock appointment times are stored in; PHP's own timezone is UTC here, and `facilities.timezone` is not reliable), so a patient's device clock can't bypass it. Window closes at `scheduled_end`; Completed/Cancelled sessions are `ended`. A logged-in staff session is never gated. The join page shows a "Too early" popup with a live countdown and connects automatically when the window opens.
- **Providers join in a NEW browser tab**, not inside the EHR: `window.openTelehealthTab(url)` / `window.openTelehealthForAppointment(apptId)` (top level in app.js, used by the `#telehealth` Join button, post-invite auto-open and the calendar popup's "Launch Telehealth Session"). The embedded Jitsi pane and `startJitsiSession` were removed - don't reintroduce them; the provider must keep the chart/plan open during the call.

## Dashboard conventions (Oct 2026)

- **`#dashboard` is the "Clinical & Operations Dashboard"** (`public/modules/dashboard.php`, `initDashboardHandler()` at top level of app.js, `dash-` CSS prefix at the end of `css/modules/dashboard.css`; the older `.stat-card`/`.dashboard-table`/`.badge-*-light` rules there are unused by it - grep before deleting, `.stat-card` also exists in theme.css). - **One request: `GET /api/dashboard/summary`** (`DashboardController::summary`). All numbers are SQL `COUNT`s - never reintroduce loading the full patient list to count it. Only today's schedule decrypts PHI. "Today" is MySQL `CURDATE()` (PHP is UTC here). **Role scoping is server-side:** Doctor/Nurse see their own schedule, appointments and notes; Billing Staff gets no schedule/clinical/referral/recall blocks; billing keys (`kpis.billing_attention`, billing rows, `billing_claims` series) exist only for Super Admin/Doctor/Billing Staff (same roles as `unbilledEncounters`). - **Definitions match the module each row links to:** *Notes waiting for signature* = `encounter_status='ready_for_sign'` and unlocked (the Encounters "Ready to sign" stage); *Overdue recalls* = Pending with `target_date < today` (scoped like `RecallController::all`); *Billing attention* = signed-not-invoiced encounters + overdue open invoices + Rejected/Denied claims. The Cardiology build deliberately has no "Treatment plans / Assessments" rows (behavioral-only). When a new work queue is added, add its row to `needs_attention` in the controller, not in JS.
- **Create New Patient** (dashboard button) links to `#patients?action=register`; `initPatientsHandler` opens the create popup and strips the param (`history.replaceState`). **Schedule Appointment** calls the top-level `scheduleOnDate(today, '', null, null, onSave)`.
